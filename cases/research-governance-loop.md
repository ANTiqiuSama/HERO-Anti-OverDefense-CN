# 跨类型案例：实验治理吞掉了实验本身

**要求：** 使用已有数据和缓存继续改进模型，减少无效封装，并保持确认性实验的科研严谨。

**发生了什么：** Agent 的确继续改进了模型，也遵守了后续的零下载要求；但探索阶段仍不断创建新版本、冻结脚本、哈希、调用清单、审计文件以及对应测试。用户的纠偏被缩窄成“不要下载”，没有变成“让实验重新成为主线”。

**为什么可能过度：** 单个冻结或哈希可能完全合理，问题出在阶段错位。探索还在频繁改变假设时，每个小版本都按发布候选治理，会产生新的维护对象；这些对象又要求测试和复验，流程可以自行繁殖。

**更合适的做法：**

1. 探索阶段复用一份实验账本，记录假设、配置、指标和保留/停止决定；
2. 只有选出候选并准备进入独立测试时，冻结一次模型和决策规则；
3. 发布给真实消费者时，再生成清单、哈希和完整可复现包；
4. 用户提出“减少封装”后，把它锁存为当前阶段约束，而不是只执行同时出现的某个字面限制；
5. 每个新版本必须对应新假设或新证据，版本号本身不算进展。

**反例：** 候选已经选定，即将运行不可重复或必须避免测试集泄漏的独立评估。此时冻结配置、绑定输入摘要并保存一次审计记录，是确认性实验的一部分，不是范围膨胀。
